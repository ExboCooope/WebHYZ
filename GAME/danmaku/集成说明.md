## 2. 数据流

```
引擎 _hit_pool ──gather()──► 归一化子弹数组
        │                         │
        │                    [视界层] vision(ctx, view)   ← 只筛真实弹、给 id、打 p/q
        │                         │
        │                    ctx.real（视野内的真实弹）
        │                         │
        │              ┌──────────┴──────────┐
        │        弹链识别器                弹团识别器
        │     (danmakuChainRecognizer)   (danmakuStableRecognizer)
        │              │                      │
        │         ctx.groups += {type:"group", source:"chain"|"stable", …}
        │                         │
        └──────────────► commit(ctx) ──► history（tracks / models / groups）
                                        │
                                   overlay.draw()
```

**约定（都已定死，改之前先看）**

- 识别器**只写 `tags`、只追加 `type:"group"`**，不删弹、不改数组顺序；
- 一个真实弹可同时属于多个组，`b.tags.group = [组id…]`、`b.tags.stable = 组id`；
- 弹组不参与视野过滤，由生成者用 `ttl` 续命；
- `model` 跨帧持久（`begin()` 从 `history.models` 装回，`commit()` 写回）；
- 识别器可声明 `interval`，降频帧走 `idle()` 自行续命。

## 3. 引擎侧取数（**最容易出错的地方**）

唯一可信写法在 `GAME/danmaku/testdata/capture-frame.mjs:52-80`：

```js
for (i=0;i<_hit_pool.length;i++){
  o=_hit_pool[i];
  if(!o || !o.hitdef || !o.hitdef.rpos) continue;     // 没有判定体的跳过
  if(o.type===stg_const.OBJ_ENEMY) continue;          // 敌机不算子弹
  x=o.hitdef.rpos[0]; y=o.hitdef.rpos[1];             // 坐标在 hitdef.rpos！
  vx=(o.move&&o.move._speed)?o.move._speed[0]:0;      // _speed 是数组
  vy=(o.move&&o.move._speed)?o.move._speed[1]:0;
  r=(h.type===0?h.range:(h.re||h.rs||0));             // 圆取 range，椭圆取半轴
  age=o.frame;
  color=(o._obj||o).color;
}
```

自机：`stg_players[0].pos[0] / .pos[1]`（**不是 `player.x/y`**）。

这些我最初都写错过（`stg_bullets`、`b.x`、`_speed_x`），表现是 `visible=0`、`groups=0`——集成时若又出这个症状，先怀疑取数。

**这段只是「圆判定」的取法。** 真正的实现现在在 `danmaku_group_overlay.js` 的 `gather()` 里，
它在上面这套取法之上补了两件事（2026-10-30）：

| 判定 | 引擎里长什么样 | `gather()` 怎么处理 |
|---|---|---|
| `hitdef.type==0` 圆 | `range` 就是半径 | 直接当弹 |
| `hitdef.type==1` 激光 | `rpos + rdir + ls/le + rs/re`，是一条**光束** | `danmakuLaser.fromHitDef` + `expand` 采样成等距伪子弹（一条 200px 的光束 ≈ 19 个点），否则整条激光只剩起点上的一个小点 |
| `hitdef.type==2` 椭圆 | `rs/re` 是两条半轴（**沿 `dir` 的是 `re`**，见 `STGCORE.js` `stgDist` 的 type 2 分支） | `danmakuShape.applyHitDef` → `hx/hy/skey`，代表半径取长轴 |
| `hitdef.type==3` 环 | `range` = 外半径，`rs` = 内半径 | `skey="g…"`、`r=range`、`inner=rs` |

`skey` 是弹种键：聚类/弹团只允许同一个 `skey` 的弹互相连边（以前只比半径，
大玉 42px 的窗口会把旁边一圈小玉全吞进来，聚出来的是"贴脸的一堆弹"而不是弹团）。

## 7. 算法侧踩过的坑（改算法前必读）

1. **转角公式**：`angle(q→p2) − angle(q→p1)` 是错的，正确是 `angle(p1→p2) − angle(q→p1)`；错一半会让链绕到 Boss 背面。
2. **弹龄必须参与外推**：只按位置预测会跨波跳变（4 发扇变成 5 发）。
3. **弹种要硬约束**：半径/颜色不同直接不许连，不能只加代价。
4. **特征步长的角度要 `wrapPi`**：跨 ±π 会让步长爆炸、均分掉到 0。
5. **W2 铺满 360° 的首尾重复弹**：两发坐标相同，测量前要剔掉。
6. **甩弹必须转角不为零**：`turn≈0` 的直线不能叫甩，只能是多重（沿弹道）或复数（斜排）。
7. **`gap` 用局部间距算**：`min(步长, 局部间距) − 2×弹径`，否则大玉那种“直径 > 间距”的弹幕会被算成能钻。
8. **画图别复用文件名**：浏览器按路径缓存，脚本已改成 `HHMMSS` 命名；`dump-groups.mjs` 必须带 `gen` 字段，否则曲线退化成连直线。

## 9. 本轮集成修复记录（2026-10-30）

### 9.1 激光：一条光束被当成一个小点（P0）

**证据**：在真引擎里 `new StraightLaser(...)` 打开后，`_hit_pool` 里确实出现 `hitdef.type=1`、
`rpos=[192,60] ls=0 le=200 rs=re=8`，而 `gather()` 只产出**一条**记录
`{x:192, y:60, r:8, vx:0, vy:0}` —— 200px 长的光束在分类里只剩起点上一个 8px 的点，
其余整条都是"安全区"。

**修法**：`gather()` 遇到 `type==1` 不再当弹，改交 `danmakuLaser.fromHitDef(h)`（处理 `le<ls`、
负长度、`rdir`、两端半宽），再 `expand()` 成等距伪子弹（间距 ≥ 半宽，单条最多 48 点）。
管线里给这些点 `laser:1`；`vision()` 不按点裁它们（否则一条光束被视野框剪成半根），
`decompose()` 让它们无条件参与种子（光束在余光里也要认出来）。
弹链识别器会把一条光束认成一条"多重弹"链，并打 `tags.laser=1` + `tags.width`，
overlay 用 `#ff5e5e` 按光束宽度画。

**效果**（headless 真引擎，合成 StraightLaser）：`gather()` 的记录数从 682 → 699（+17 个采样点），
`ctx.groups` 里稳定出现 `chain:multi n=19 laser=1`。

### 9.2 椭圆 / 环：字段名完全对不上（P0）

`danmaku_shape.js` 原来只认 `{rx,ry,rot}`，引擎给的是 `{type,rs,re,dir}`，所以它永远只会
"从 r 推出一个圆"。现在加了 `fromHitDef()`：

- 椭圆（type 2）：沿 `dir` 的半轴是 **`re`**，垂直方向是 `rs`（这是照 `STGCORE.js` `stgDist`
  的 type 2 分支推出来的：`a·dl² + b·dd² = a·b`，`dl` 沿 `dir` → 该方向半轴 = `sqrt(b) = re+r`）；
  再按旋转角度算轴对齐包围盒 `hx/hy`，代表半径取长轴。
- 环（type 3）：`range` 是外半径、`rs` 是内半径，`skey="g…"`，额外给 `inner`。
- 弹团聚类要求 `skey` 一致 —— 这条顺带修掉了"大玉把周围小玉一起吞进弹团"的老毛病
  （`r=14` 的窗口是 42px，`_clump` 原型里那个 33 发的团半径集是 `6/4/14`，就是这么来的）。

### 9.3 单帧 531ms → 40~50ms：`decompose` 的两个 O(n²)（P2 但影响最大）

**证据**：phase5 密集帧实测 `stats.ms`（只算识别器）**531ms**；离线对同一帧跑
`decompose`：200 发 58ms、400 发 211ms、700 发 606ms、1344 发 1791ms —— 明显超线性。

**根因**：两条 O(种子的每一步 × 全部子弹) 的全表扫描，而 `_dg_buildIndex/_dg_near`
这两个网格索引函数**建了却从来没人调用**：

1. `_dg_extend` 每走一步都遍历整个 `list` 找下一点 → 换成按**发弹点**建的网格索引
   （链外推本来就在发弹空间里做），查询半径 `pos_tol×√2` 覆盖原来的双轴容差，**结果完全一致**。
2. 种子生成、`_dg_localSpacing` 也在做全表扫描 → 种子改用位置网格，
   局部间距改成"半径自适应加倍，凑够 k 个最近邻"（结果与原全量扫描一致）。

**效果**：700 发 606 → 73ms，1344 发 1791 → 284ms（8 倍）；`danmaku-group.mjs` 的
13 条候选/13 组/各项数字一字不变；真机 phase5 的 `stats.ms` 从 531ms 降到 42~50ms。

### 9.4 `history.tracks` 只增不减（内存 + 每帧线性扫描）

`commit()` 之前只写不删，而引擎弹对象没有 `id`，所以 `vision()` 的 `_matchId` 对**每一发弹**
都要线性扫一遍整个 tracks。实测 1200 帧后 tracks 长到 900 条且不再回落；密集帧按 2000 发/帧
算，几分钟就是几万条 × 每帧几千发 = 上千万次比较。

修法：`commit()` 只保留本帧出现过的 id（上一帧消失的立刻删）；`_matchId` 改成按位置建网格
索引再查近邻（门限内的最近邻，语义不变，span 随门限放大）。
实测 tracks 回落成"当前可见弹数"（27~677），`danmaku-pipeline.mjs` 的 id 复用仍是 79/79。

### 9.5 开关与上限（P1）

`stg_show_danmaku_group`（默认 0，和 `stg_show_hitbox` / `stg_show_danmaku_ai` 一致）、
`stg_danmaku_group_max_chains`、`stg_danmaku_group_max_clumps`、`stg_danmaku_group_interval`
都进了 `STGGLOBAL.js`，运行期控制台改、下一帧生效。关掉时 `step()` 直接返回，
**整条管线不跑**（密集帧那 30ms 也就没了）。

另外：单帧 >25ms 自动把重算间隔放到 4，>50ms 放到 6（`danmakuGroupView.iv`），
`danmakuGroupView.perf` 里给了 `gather/vision/run/total` 分阶段耗时，方便下次定位。

### 9.6 可收集道具被当成弹幕（2026-10-30 补）

**症状**：Boss 每转一个阶段、杂鱼每死一只，都会 `gCreateItem` 掉 10 个 `ITEM_SCORE` + 10 个
`ITEM_POWER`（`GAME/default_item_script.js:36`）。这些道具在引擎里是
`type=OBJ_ITEM(4)`、`side=SIDE_ENEMY`、`hitdef.range=4` —— 有**判定体**、还是**敌方阵营**，
于是 `gather()` 的两条过滤（"不是敌机"、"不是自机子弹"）一条都拦不住它：
道具作为"半径 4 的小玉"进入分类器，被连进弹链、算进 `visible`、还挤占弹链名额。

**还有一种更大量的**：击破（Boss 死亡 / 符卡结束）时 `stgDeleteSubShot(parent, true)`
（`GAME/default_lib.js:860`，`boss_slz.js` 里二十多处）把 Boss 名下的子弹逐发
`deleteShotToItem` → `gCreateItem(shot.pos, ITEM_BLT, …)` 变成**绿点**
（`content={point_bonus:1}`）。**这一类是同一个 `gCreateItem` 造出来的，`type` 照样是
`OBJ_ITEM`、`side` 照样是 `SIDE_ENEMY`、`hitdet.range` 照样是 4**，所以同一条过滤就管住了。
它比掉落道具更危险：场上 140 发弹会一口气变成 140 个点，全部落在子弹原来的位置上。

实测（headless，phase2）：

| 场景 | `_hit_pool` 里道具 | `gather()` 取到道具 | 同帧取到真弹 |
|---|---|---|---|
| 转阶段掉落 12 个（修复前） | 12 | **12**（道具自己凑出过 `chain:sweep n=3`） | — |
| 转阶段掉落 12 个（修复后） | 12 | **0** | 72 条 |
| 击破：141 发弹 → 150 个绿点 | 150 | **0** | 0~20（旧弹已被清空，新一波照常取到） |

**修法**：`gather()` 里加一条 `if (o.type === stg_const.OBJ_ITEM) continue;` ——
和 `danmaku_ai.js:82`（AI 侧的取数）本来就是同一条规则，只是新的弹组 overlay 漏抄了。
按 `type` 而不是按 `content`/贴图来判断，是因为绿色/黄色、py值/点数这些只是 `content` 不同，
引擎给出的是同一个 `OBJ_ITEM`。
注意这里**不能**改成"只认 `OBJ_BULLET`"的白名单：IFE 包的 `Blocker_Line` 用的是
`OBJ_NONE` + 激光判定 + `SIDE_TERRAIN`，是玩家会撞的墙，白名单会把它们一起丢掉。

### 9.7 顺手修掉的

- `danmaku_stable.js` 用了 `Math.hypot`（ES6）→ 换成 `sqrt`，和"纯 ES5"的约定一致。
- `attach()` 里立刻 `ensureOnTop()` 一次：原来要等第 30 帧才把 UI 画布拉回上层，
  进关头半秒 overlay 是被 frame 画布压住的。
- 弹团识别器写 `tags.stable` 前先确保 `tags` 存在（单测/外部调用喂裸弹时不再抛）。

## 10. 单卡适配：夜盲之歌（把"眼睛"挪走的那张）

### 10.1 这张卡特殊在哪

`BossSLZ.Spell3`（`boss_slz.js:777`，名字 `记忆【夜盲之歌】`）在 `frame==60` 挂
`new NightEffect(this, 30, 120)`。这个特效不改任何物体坐标，只在渲染层（layer 74）把整块画面
压黑，然后用 `hyzCircleBlendShader` 把**一小圈**原画面贴回去：

```glsl
q = smoothstep(uSize[0], uSize[1], d);          // d = 到灯心的距离
gl_FragColor = uColor*q + (1-q)*smpColor;       // uColor = [0,0,0,0]
```

- `uSize = [size1, size2] = [30, 120]` → 30px 内全亮，30~120 渐暗到全黑，再外面纯黑；
- 灯心 = `NightEffect.ph[i].pos`，它是 `PlayerHolder`：出生在**自机位置**，
  用 `luaMoveTo` 在 60 帧内挪到 `(stg_frame_w/n/2 + stg_frame_w/n*i, stg_frame_h/2)`。

真机实测（1 自机，场地 384×448）：

| | |
|---|---|
| 眼（灯心） | 自机 (192,358) → **(192,224) 场地正中**，第 60 帧到位 |
| 自机到眼 | **134px**，已经出了 `size2=120` → **自机整个在黑暗里** |
| 2 自机 | `ph[0]=(96,224)`、`ph[1]=(288,224)` → 左右两只眼 |

结论：这张卡上"玩家能看见什么"和"自机在哪"**彻底解绑**。分类器原来用
`viewFor(player)`（自机上方 120×220 的方框）算视野，在这张卡上是错的——
它算的是自机旁边那块黑，而玩家实际盯着场地中间那盏灯。

### 10.2 适配做法（`danmaku_group_overlay.js`）

1. **认卡**：`_eyeOf()` 在 `_pool` 里找 `instanceof NightEffect` 且带 `size1/ph` 的活对象
   （每 60 帧重扫一次，平时只读坐标；`active` 变 0 就立刻退回矩形）。
   不 import 任何卡片代码，只读它的公开字段，卡片侧零改动；IFE 这类没有 `NightEffect` 的包自然走不到。
2. **换锚点**：视野中心从"自机位置"换成 `ph[玩家序号].pos`。
   序号按 `stg_players` 里找到该自机的下标来定——**分类器绑在哪个自机，就用哪只眼**，
   所以 2 人模式（假设以后要）绑的是 `ph[0]` 或 `ph[1]`，不会两只眼混用。
3. **换形状**：视野从矩形变成圆 —— `precise` 用 `size1=30`（全亮），`periphery` 用 `size2=120`（渐暗）。
   为此 `danmaku_pipeline` 与 `danmaku_group` 的视野判定都加了圆分支
   （`{cx,cy,r}` → 比距离；矩形 `{x,y,w,h}` 照旧），`view.kind` 标成 `"eye"`。
4. **裁剪绘制**：`draw()` 在眼睛模式下先 `arc + clip` 到 `periphery` 圆再画弹链/弹团。
   不裁的话 overlay 会画在 UI 画布（layer 81~100，在特效的 74 之上），
   等于用调试层把玩家本来**看不见**的弹幕照亮了。视野边界也改成画两个圆（灯心/渐暗圈）。

### 10.3 实测效果（headless，phase2 里手动挂 `NightEffect(boss,30,120)`）

```
视野=eye 灯心r=30 渐暗r=120 眼=(192,224) 机=(192,358) 眼机距=134
场内敌弹 灯内 164 / 灯外 417 → 分类器可见 163，组 4
```

也就是 581 发里只有灯内那 164 发进分类器（163 与 164 差的是取数那一帧的抖动），
灯外的 417 发不再参与识别、也不会被画出来。灯心 30px 内通常没几发，
所以链识别器会走它自己的降级路径（精确视野为空 → 拿余光当种子），这在这张卡上正好是对的。

### 10.4 没有做的

- **AI 侧 overlay（`danmaku_overlay.js`/`danmaku_ai.js`）仍以自机为锚点**：这张卡上它的
  "视野"依然在黑暗中。要改是同一套（把 `view` 换成 `kind:"eye"`），没做。
- **2 自机没有实测**：只按 `ph[i]` 下标实现了，没有真机双人环境验证过。
- **灯心的 60 帧移动过程**：这 60 帧里灯心在飞，视野跟着飞（每帧读一次坐标），
  没有做插值/预测。
